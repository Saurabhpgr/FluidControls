# FluidControl ETMS — Employee Code Policy & Architecture Guide

## 1. Executive Summary & Core Principles

In FluidControl ETMS, every employee is assigned a permanent, unique, and immutable identifier: `employee_code`.

The system strictly enforces three non-negotiable architectural invariants:

1. **Uniqueness**: No two employees (active or deactivated/retired, past or present) can ever share the same `employee_code`.
2. **Immutability**: Once created, an `employee_code` cannot be altered, overwritten, or reassigned by any user, admin, frontend UI action, or direct REST API / RPC call.
3. **Consistency Everywhere (Single Source of Truth)**: `employee_code` is stored solely on the `employees` table. Every downstream module (training schedules, attendance, quiz results, training history, audit logs, notifications, PDF/Excel exports, emails) references `employees.id` via Foreign Key (`employee_id`) and resolves the code dynamically.

## 2. Database-Level Enforcement (PostgreSQL / Supabase)

### 2.1 Format & Sequence-Based Generation
- **Format Pattern**: `^FC[0-9A-Za-z_-]{2,}$` (e.g., `FC001`, `FC010`, `FC101`). Enforced via database constraint `check_employee_code_format`.
- **Server-Side Generation**: Codes are generated by the PostgreSQL sequence `employee_code_seq` wrapped in `generate_employee_code()`. The frontend never guesses or increments codes on the client side, eliminating race conditions and duplicate collision bugs.
- **Default Expression**: `employees.employee_code DEFAULT generate_employee_code()`.

```sql
CREATE SEQUENCE IF NOT EXISTS employee_code_seq START WITH 101;

CREATE OR REPLACE FUNCTION generate_employee_code()
RETURNS text AS $$
DECLARE
  next_val bigint;
  new_code text;
  code_exists boolean;
BEGIN
  LOOP
    next_val := nextval('employee_code_seq');
    new_code := 'FC' || LPAD(next_val::text, 3, '0');
    SELECT EXISTS(SELECT 1 FROM employees WHERE employee_code = new_code) INTO code_exists;
    IF NOT code_exists THEN
      RETURN new_code;
    END IF;
  END LOOP;
END;
$$ LANGUAGE plpgsql;
```

### 2.2 Permanent Immutability Trigger
To prevent modification from any source (including direct Supabase API requests, developer console tampering, or bulk update scripts), a `BEFORE UPDATE` trigger enforces strict immutability:

```sql
CREATE OR REPLACE FUNCTION prevent_employee_code_mutation()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.employee_code IS DISTINCT FROM OLD.employee_code THEN
    RAISE EXCEPTION 'employee_code is permanent and immutable (Attempted to modify from % to %). Code modifications are strictly prohibited.', OLD.employee_code, NEW.employee_code;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_protect_employee_code
BEFORE UPDATE ON employees
FOR EACH ROW EXECUTE FUNCTION prevent_employee_code_mutation();
```

### 2.3 Deactivation & Anti-Reuse Guarantee
- FluidControl ETMS utilizes soft deactivation (`employees.is_active = false`).
- Retired and deactivated employees remain in the `employees` table permanently.
- Because of the global `UNIQUE` constraint, retired employee codes are never recycled, reassigned, or made available for reuse.

## 3. Application-Level UI & Import Enforcement

### 3.1 User Interface Behavior
- **Add Employee Dialog**: The `employee_code` input field is completely read-only, styled as auto-generated with a lock badge. The UI omits `employee_code` on insert so the server-side sequence safely assigns it upon creation.
- **Edit Employee Dialog**: The `employee_code` field is permanently locked with a lock badge, styled as immutable, and omitted from the update payload.

### 3.2 Bulk Spreadsheet Import Rules
- External employee codes (e.g. from HR master files) can optionally be supplied or left blank for system auto-generation.
- **Validation Pipeline**:
  1. Validates format against regex `^FC[0-9A-Za-z_-]{2,}$`.
  2. Detects and flags duplicate codes within the uploaded file.
  3. Validates uniqueness against all database records (both active and deactivated/retired employees).
  4. Any row containing an existing/retired code is rejected with an explicit per-row error: `"Code already in use by active/retired employee (immutable)"`.

## 4. Exceptional Out-of-Band Correction Protocol

In the extraordinary event of a legal name change, corporate acquisition ID migration, or typographical correction requiring an `employee_code` adjustment:

> [!CAUTION]
> **Out-of-Band Migration Protocol Only**:
> 1. Corrections can **never** be performed through the application UI or standard API endpoints.
> 2. Requires written sign-off from the HR Lead and Systems Administrator.
> 3. Must be executed in a logged, auditable database transaction by a superuser:
>    ```sql
>    BEGIN;
>    -- Temporarily disable immutability trigger for the single transaction
>    ALTER TABLE employees DISABLE TRIGGER trg_protect_employee_code;
>    
>    UPDATE employees 
>    SET employee_code = 'FC-NEW-CODE' 
>    WHERE id = 'TARGET-EMPLOYEE-UUID';
>    
>    -- Re-enable immutability trigger immediately
>    ALTER TABLE employees ENABLE TRIGGER trg_protect_employee_code;
>    
>    -- Insert audit log entry
>    INSERT INTO audit_logs (action, entity_type, entity_id, details)
>    VALUES ('employee_code_superuser_correction', 'employee', 'TARGET-EMPLOYEE-UUID', 
>            '{"reason": "HR Signed Legal Correction", "old_code": "FC001", "new_code": "FC-NEW-CODE"}');
>    
>    COMMIT;
>    ```
> 4. Because all downstream tables join live on `employee_id` (FK), the corrected code will immediately and consistently reflect in all historical training records, attendance, quiz scores, and reports with zero orphaned records or data drift.
